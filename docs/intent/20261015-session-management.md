# Intent / 意图：PostgreSQL 与 MySQL 会话查看和终止
最后修改时间: 2026-10-15 11:55:10

## Review status / 审查状态

## Background / 背景

用户删除 PostgreSQL 数据库时遇到其他会话占用。现有 `schema drop --force` 已支持通过原生 `WITH (FORCE)` 尝试断开连接并删除数据库，但缺少独立查看占用者、终止指定会话，以及在保留数据库时断开连接的入口。

前序评估建议在 `dbtalk postgres`、`dbtalk mysql` 下增加 `session list` 和 `session kill`。用户要求使用 SpecFlow 记录任务，并明确两类命令沿用现有目标数据库选择习惯：显式 `--database` 优先，否则从 DSN 读取 database，两者都没有时失败。用户随后补充可选 `--wait`，明确不实现 `session cancel`。

用户已确认“验证有效”，并要求完成 SpecFlow 验证文档；实现交付已接受，进入整体 Verification。具体设计见已接受的同名 [Plan](../plan/20261015-session-management.md)，验收结果见同名 [Verification](../verification/20261015-session-management.md)。阶段确认不代表已提交或发布。

## Goals / 目标

- 为 PostgreSQL 和 MySQL 提供 `session list`、`session kill`，在明确的目标数据库范围内查看、终止客户端会话。
- 两类命令统一采用 `--database > DSN database > 失败`，避免遗漏目标时扩大到整个实例。
- 支持按会话 ID 终止，以及终止目标数据库范围内的客户端会话；按 ID 操作仍受目标数据库约束。
- 为 `kill` 提供可选的 `--wait SECONDS`，区分终止请求已发送、已确认退出和等待超时。
- 沿用现有 DSN 选项、破坏性操作确认、错误处理和根命令 verbose 日志习惯。
- 复用现有集中配置系统，轮询间隔等运行策略通过 typed 配置、YAML 和环境变量覆盖提供，不在业务代码写死。

## Non-goals / 非目标

- 不实现 `session cancel`，不增加仅取消当前 SQL、保留连接的执行模式。
- 不提供无数据库范围的实例级批量终止，不追踪并持续终止连接池新建的连接。
- 不修改数据库、账号、授权或连接池配置，不把会话管理并入删库流程。
- 不自动提权或授予会话终止权限，不引入跨方言管理框架。
- 不连接或终止真实业务会话，不安装、发布或同步用户级插件；开发实验仅使用明确准备的隔离测试实例。

## User stories / scenarios / 用户故事 / 场景

1. 管理 DSN 指向 `postgres` 或 `mysql`，用户显式传入 `--database app`；列表和终止操作以 `app` 为目标。
2. DSN 指向 `app`，用户省略 `--database`；列表和终止操作均使用 DSN 中的 `app`。
3. DSN 没有 database，用户显式传入 `--database app`；目标解析成功，后续连接和操作仍须满足原生服务端要求。
4. 两种来源都没有 database，即使提供了 `--id` 或 `--yes`，命令也在查询或终止会话之前明确失败。
5. 用户先查看目标数据库的活跃及空闲连接，再按 ID 或数据库范围确认终止；其他数据库中的会话不成为执行目标。
6. 用户提供 `--wait SECONDS`，命令等待本次目标会话退出；未提供时只报告终止请求结果。等待超时与权限失败不能被报告为全部终止成功。

## Command boundaries / 命令边界

拟议命令组为 `dbtalk postgres session` 和 `dbtalk mysql session`，两种引擎使用相同的目标选择契约。

| 项目 | 约束 |
| --- | --- |
| 连接参数 | 沿用 `--dsn` / `--dsn-env` 必须且只能提供一个的约定；命令引用已有变量，不新建 `.env` 或改写已有凭据。 |
| `list --database NAME` | 参数可省略；省略时从 DSN database 取值。解析后必须有明确目标，仅列出该范围内当前账号可见的客户端会话，包含空闲会话。 |
| `kill --database NAME` | 与 `list` 采用相同优先级。省略 `--id` 时，以解析后的数据库范围选择客户端会话。 |
| `kill --id ID` | 在已解析的目标数据库内进一步选择会话；`--id` 不与 `--database` 互斥，也不能跳过数据库解析。ID 属于其他数据库时拒绝执行。 |
| 执行确认 | 拟沿用 `schema drop`、user/role 管理的 `--yes` 约定；未确认时返回参数错误，不发送终止请求。 |
| `kill --wait SECONDS` | 可选，显式提供正秒数时有界等待本次目标会话退出；省略时不主动等待退出。该参数不用于 `list`。 |
| 日志 | 仅根命令 `dbtalk -v/--verbose` 启用 stderr logging；子命令不增加 verbose 开关。 |

显式提供的空白或无效 `--database` 应校验失败，不静默回退到 DSN database。两者都没有时，应产生可理解的 CLI 错误及非零退出码，不依赖 Python `assert`。

数据库解析结果是会话筛选、按 ID 核对和批量终止的共同范围约束。不得因 ID 可在实例范围查询而绕过该约束，也不得在缺失目标时退回当前管理连接的默认库或整个实例。管理连接的具体建连方式由 Plan 依据现有方言实现确定。

MySQL 的会话 database 表示当前默认数据库：一个会话仍可使用限定名称访问其他数据库，或尚未选择默认库。因此 MySQL 的数据库筛选不等同于枚举所有访问该库或持有该库对象锁的连接。列表、终止和用户手册必须采用同一解释。

`kill` 终止整个连接；PostgreSQL 使用 `pg_terminate_backend`，MySQL 使用 `KILL CONNECTION`。两者的默认成功响应都不应被直接解释为连接已经退出。等待只针对本次选定的会话，不自动纳入连接池随后新建的连接；具体等待预算和批量调度设计在 Plan 中收敛。

## Acceptance criteria / 验收标准

- A01：PostgreSQL、MySQL 均提供 `session list` 和 `session kill`；目标数据库解析覆盖显式覆盖 DSN、仅显式指定、仅 DSN 指定和两者缺失四种情形。
- A02：两者缺失或显式参数无效时，在会话查询和终止之前返回清晰错误和非零退出码；按 ID 操作也不能绕过该检查。
- A03：`list` 仅列出目标数据库范围内可见的客户端会话，包含空闲连接，并展示会话 ID、数据库、用户、客户端与状态等基本信息；不将权限受限的结果承诺为完整实例视图。
- A04：`kill --id` 只允许终止目标数据库内的会话；按数据库批量选择不扩大到其他数据库。执行命令自身及后台、复制等系统会话不进入终止目标，实际执行前重新核对目标。
- A05：`kill` 必须提供 `--yes` 才发送终止请求；权限不足、会话消失和批量部分失败等结果能明确区分，失败不被汇总为全部成功，不承诺已终止操作可以整体回滚。
- A06：`kill` 接受可选 `--wait SECONDS`。未提供时准确报告请求结果；提供时有界等待并核对退出，超时明确报告尚未退出的目标并返回非零退出码，不持续追杀新连接。
- A07：仅根命令 `-v/--verbose` 启用日志，记录操作范围、会话标识、结果与耗时，不记录密码、完整 DSN 或会话 SQL 文本；stdout 保留列表和操作结果。
- A08：不注册 `session cancel` 或仅取消 SQL 的模式；手册和仓库内 Agent skill 同步数据库优先级、MySQL 筛选含义、终止与等待语义。相关开发检查与必要隔离实验提供实际证据。
- A09：轮询间隔由现有配置系统加载和校验，YAML 与环境变量覆盖均生效；查询与执行超时复用已有配置，不在命令或轮询代码中增加固定秒数及备用默认值。

## Workload assessment / 工作量评估

主要交付为两种引擎遵循同一数据库范围契约的会话管理能力，覆盖 CLI、原生查询与终止、可选等待、结果呈现、日志和文档。现有 SQLAlchemy 连接管理、`DbtalkGroup`、DSN 解析、错误脱敏与表格输出可复用。

- 工作量：中等。预计在两个方言包各增加会话管理模块，在对应 `cli.py` 注册命令，并按实际需要扩展统一日志白名单及测试、手册、仓库内 skill。
- 复杂度：中等。目标选择规则简单，但 PostgreSQL 与 MySQL 的会话标识、权限可见性、系统会话识别和退出确认不同；等待及部分失败需要明确结果契约。
- 风险：较高。终止连接会中断业务及事务，无法通过代码回滚恢复已断开的会话；重点验证数据库范围、按 ID 核对、自身与系统会话排除、确认和超时行为。
- 关键技术核实项：PostgreSQL 的可见字段与终止权限；MySQL 当前支持基线下的会话来源和权限；会话身份变化、异步退出及有界等待的实现。此类选择由 Plan 处理，不作为已验证事实。
- 检查范围：使用现有 Ruff format/check、Mypy、pytest 入口；覆盖主要成功路径和上述实际风险边界，并在明确的隔离环境证明两种引擎的实际退出行为。模拟连接检查不能替代真实退出证据。
- 审查上下文：目标解析、方言会话查询与终止 SQL、等待状态及退出码、日志输出，以及手册对范围限制的说明。

结论：保持单任务，由主会话顺序推进。两种方言共同交付同一套范围和等待契约，共享 CLI 约定、日志与验收；当前无需为方言适配增加交接和集成节点。后续若技术调查扩大实现边界，再于 Plan 重新评估拆分。

## Risks / assumptions / 风险 / 假设

- 查看会话与终止会话是不同权限；账号可能只能看见部分字段或部分会话，不自动授予额外权限。
- 会话可能在列表、执行和等待之间退出或发生身份变化；结果应如实报告，不承诺跨命令快照冻结或完全消除 ID 复用竞争。
- 终止可能已经生效但清理尚未结束；权限错误、异步退出及等待超时需要与成功退出区分。
- 连接池可能立即重连；一次数据库范围的终止和等待不能保证数据库持续无连接，也不替代 PostgreSQL 原生强制删库。
- MySQL 按默认数据库筛选有原生覆盖限制，不能宣称已经释放目标数据库全部锁或全部使用者。
- 批量终止不能整体回滚；业务事务和非事务操作的最终状态由数据库原生行为决定。
